## 1. 项目概述

### 1.1 项目定位

Crush 是一个**终端优先（Terminal-First）的 AI 编码助手**，由 Charmbracelet 团队开发。它提供基于会话的 AI 编程辅助功能，支持多种大语言模型（LLM），具备代码编辑、文件操作、Shell 命令执行、MCP 工具集成、LSP 诊断等能力。用户可以通过精美的终端 TUI 界面或非交互式命令行模式与 AI 进行对话。

### 1.2 核心能力

- **多模型支持**：OpenAI、Anthropic、Google、Azure、Bedrock、OpenRouter、Vercel、Hyper 等 9+ 提供商
- **会话管理**：支持多会话、会话恢复、自动摘要、消息排队
- **工具系统**：内置 20+ 工具（文件编辑、Shell 执行、代码搜索等）+ MCP 协议扩展 + 子代理委派
- **终端 TUI**：基于 Bubble Tea 框架的现代化终端界面
- **LSP 集成**：语言服务器协议支持，提供代码诊断和引用查找
- **权限控制**：细粒度的工具执行权限管理

### 1.3 技术选型

| 技术领域 | 选型 | 理由 |
|----------|------|------|
| 语言 | Go 1.26+ | 高性能、优秀的并发模型、单二进制部署 |
| CLI 框架 | Cobra + Fang | 成熟的命令行解析，Fang 提供信号处理和版本管理 |
| TUI 框架 | Bubble Tea v2 | Charmbracelet 自研，Elm 架构的终端 UI 框架 |
| LLM 抽象 | Fantasy | Charmbracelet 自研，统一多提供商的 LLM 调用接口 |
| 模型元数据 | Catwalk | Charmbracelet 自研，提供模型能力、费用、上下文窗口等元数据 |
| 数据库 | SQLite (ncruces/modernc) | 嵌入式、零配置、适合本地应用 |
| SQL 生成 | sqlc | 类型安全的 SQL → Go 代码生成 |
| 数据库迁移 | Goose | 轻量级数据库迁移工具 |
| MCP 协议 | go-sdk (modelcontextprotocol) | 官方 Go SDK，支持 MCP 工具扩展 |
| LSP 协议 | jsonrpc2 + Powernap | JSON-RPC 2.0 通信 + 语言服务器管理 |
| Shell 执行 | mvdan.cc/sh | 纯 Go 实现的 POSIX Shell 解释器，跨平台兼容 |
| 事件上报 | PostHog | 匿名使用数据收集（可禁用） |
| 样式渲染 | Lip Gloss v2 | Charmbracelet 自研终端样式库 |

### 4.1 Agent 模块（核心编排层）

Agent 模块是整个系统的核心，采用**两级编排架构**：`Coordinator` 负责全局协调，`SessionAgent` 负责会话级执行。

**设计模式**：
- **策略模式**：`Coordinator.buildProvider()` 根据提供商类型动态构建不同的 LLM 客户端

- **队列模式**：`sessionAgent.messageQueue` 实现同一会话的请求排队
- **观察者模式**：通过 `pubsub.Broker` 实现消息/会话变更的事件通知

## 5. 并发模型

### 5.1 csync 包 — 并发安全数据结构

csync 包提供了三种核心并发安全数据结构，替代直接使用 `sync.Mutex`：

| 类型 | 用途 | 底层实现 |
|------|------|----------|
| `csync.Map[K, V]` | 并发安全的泛型 Map | `sync.RWMutex` + `map[K]V` |
| `csync.Slice[T]` | 并发安全的泛型切片 | `sync.RWMutex` + `[]T` |
| `csync.Value[T]` | 并发安全的单值容器 | `sync.RWMutex` + `T` |

**设计动机**：相比 `sync.Mutex`，csync 提供了：
- 类型安全的泛型 API，避免 `interface{}` 类型断言
- 读写锁分离（`RWMutex`），提高读多写少场景的并发性能
- 内置 `LazyMap` 支持延迟加载
- JSON 序列化/反序列化支持
- 迭代器（`iter.Seq`/`iter.Seq2`）支持

**在 Agent 中的应用**：

```mermaid
    subgraph "Broker[T] 架构"
        PUB["Publisher"] -->|Publish| BROKER["Broker[T]<br/>subs: map[chan Event[T]]struct{}"]
        BROKER -->|fan-out| SUB1["Subscriber 1<br/>buffered chan (64)"]
        BROKER -->|fan-out| SUB2["Subscriber 2<br/>buffered chan (64)"]
        BROKER -->|fan-out| SUB3["Subscriber N<br/>buffered chan (64)"]
    end
```

**关键设计**：
- 泛型实现，支持任意类型的事件载荷
- 缓冲通道（64），防止慢消费者阻塞发布者
- 通道满时丢弃事件（非阻塞发布），保证发布者不被阻塞
- 通过 `context.Context` 管理订阅生命周期，自动清理

### 5.3 消息排队机制

```mermaid
sequenceDiagram
    participant User as 用户
    participant SA as SessionAgent
    participant MQ as messageQueue
    participant LLM as 大模型

    User->>SA: Run(call1) [会话空闲]
    SA->>SA: activeRequests.Set(sessionID, cancel)
    SA->>LLM: Stream(call1)

    User->>SA: Run(call2) [会话忙碌]
    SA->>MQ: 入队 call2
    SA-->>User: return nil, nil (已排队)

    User->>SA: Run(call3) [会话忙碌]
    SA->>MQ: 入队 call3

    LLM-->>SA: call1 完成
    SA->>SA: activeRequests.Del(sessionID)

    Note over SA: PrepareStep 回调中处理队列
    SA->>MQ: 取出 call2, call3
    SA->>SA: 将排队消息追加到对话历史
    SA->>LLM: 继续 Stream（包含 call2, call3）
```

### 5.4 活跃请求管理

- 每个会话最多一个活跃请求，通过 `activeRequests` Map 管理
- `Cancel(sessionID)` 调用对应的 `context.CancelFunc` 取消请求
- `CancelAll()` 遍历所有活跃请求并取消
- 请求完成后自动从 Map 中移除

## 9. 关键设计决策总结

| # | 决策 | 理由 |
|---|------|------|
| 1 | **两级 Agent 架构** (Coordinator + SessionAgent) | 分离全局关注点（OAuth、配置刷新）和会话级关注点（消息管理、工具执行） |
| 2 | **csync 替代 sync.Mutex** | 提供类型安全的泛型 API、读写锁分离、JSON 序列化支持 |
| 3 | **pubsub 泛型事件总线** | 解耦服务层和 UI 层，支持多订阅者，非阻塞发布 |
| 4 | **SQLite + sqlc** | 嵌入式零配置 + 类型安全的 SQL 代码生成，适合本地桌面应用 |
| 5 | **Fantasy 统一 LLM 抽象** | 屏蔽 9+ 提供商的 API 差异，统一流式调用接口 |
| 6 | **消息排队而非拒绝** | 同一会话的并发请求自动排队，不丢失用户输入 |
| 7 | **自动摘要机制** | 根据上下文窗口使用量动态触发，避免 Token 溢出 |
| 8 | **循环检测** (SHA-256 签名) | 检查最近 10 步中工具调用签名重复 > 5 次，防止 Agent 死循环 |
| 9 | **POSIX Shell 模拟** (mvdan.cc/sh) | 纯 Go 实现，跨平台兼容，避免依赖系统 Shell |
| 10 | **MCP 协议扩展** | 支持动态加载第三方工具，遵循开放标准 |
